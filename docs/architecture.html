Design decisions

Z3 is the trusted oracle; simple_smt only translates

The soundness of every answer rests on Z3, not on simple_smt. simple_smt's job is a faithful 1:1 mapping from the Eiffel expression tree to Z3 AST nodes. That claim is grounded empirically by a test suite that proves known theorems (their negations are unsat) and refutes known non-theorems (sat with an extracted counter-model) — the same differential-grounding discipline used elsewhere in the ecosystem.

Inline C, no separate .c files

Every Z3 call is an inline-C external over z3.h in SMT_CONTEXT, following the ecosystem's inline-C pattern. Opaque Z3 handles (context, sort, ast, solver, model) are held as POINTER. n-ary Z3 operators (add, and, distinct) are bound as 2-element C arrays; wider arities fold in Eiffel (e.g. all_distinct is pairwise).

Context-lifetime AST, ref-counted solver/model

Using Z3_mk_context ties AST-node lifetime to the context, so expressions need no per-node reference counting — a large simplification. Only solvers and models are inc_ref/dec_ref managed.

Lazy memoized decisions (CQS)

Deciding satisfiability is expensive and deterministic for a fixed assertion set, so decide is a lazy memoized query: it runs Z3 only when the cached result is stale (an is_decided flag invalidated by assert/push/pop/reset) and caches otherwise. This keeps the ergonomic if smt.is_satisfiable idiom while satisfying command-query separation via the whitelisted lazy-initialization pattern, and it eliminates redundant solver calls (query-twice, or query-then-model, reuse the cache).

The prove/refute duality

prove(P) and refutation(P) are two readings of one solver call: assert not P in a scratch scope; if it is unsatisfiable, P is valid (prove returns True); if it is satisfiable, the model is a counterexample (refutation returns it). Both restore the assertion set exactly (assertions_unchanged).

Where it sits

simple_smt is Phase 0 of a correctness-tooling arc: the mechanical "dispose" beneath a propose/dispose loop. Contract verification discharges VCs through it; non-vacuity checking detects under-constrained specs through it; specification synthesis checks each refinement step through it. Everything above is orchestration; the trusted decision procedure is here.

Extension points

  • New operator: one inline-C external in SMT_CONTEXT + one fluent feature in SMT_EXPR (the mod/div/ite/xor/iff/distinct additions followed exactly this).
  • New sort (bitvector, string): a *_sort cache + constant/literal builders.
  • Quantifiers, optimization, unsat cores: additional Z3 API surface, same binding pattern.
